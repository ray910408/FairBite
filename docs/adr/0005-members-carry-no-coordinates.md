# 成員不攜帶座標

這是一個定位導向的聚餐決策 app，但只有房主在建房時提供一個座標（搜尋圓心＝出發點，見 CONTEXT.md「出發點」詞條）。成員加入（join_room）不收任何位置：引擎裡所有距離計算都是「圓心 vs 餐廳」（distFactor／rainFactor，經 snapCenter 量化起算），成員座標從未被讀取。PR #9 曾建立「全員座標中位數當圓心」的整套基礎建設（成員座標收集、凍結後刪除、24 小時 TTL 掃描），經實測取捨後整套回收，圓心改回房主位置、搜尋半徑改取全員距離偏好平均。本 ADR 將此定為刻意的產品／隱私決策：加入房間不請求定位權限、不傳送座標；出發點是「房主替聚會選的集合位置」（可為任選地點），不必然是任何人的即時位置。個人距離偏好（max_distance_m）仍逐成員生效於搜尋半徑平均（handlers.go averageMemberRadius）；計分端距離權重的逐成員變異來自 transport（engine.go travelMinutes），不是 max_distance_m。

## Considered options

- **全員座標中位數當圓心（已實作後回收，PR #9）**：對「大家都近」最直觀，但要求每位成員交出精確位置（要保護、要刪除、要解釋的個資多 N 倍）、加入流程多一個權限彈窗；實測取捨後判定收益不抵成本，整套基建一併回收。
- **成員座標收而不用（回收前的過渡狀態）**：保留未來彈性，但「收沒有用途的個資」本身就是負債，隱私面白白擴大。
- **只有房主提供出發點（採用）**：隱私面最小——全系統唯一的精確位置是 rooms.center_*（0015 欄級 grant 隱藏＋引擎側量化，見 server/weights.go 威脅模型）——加入零摩擦；代價是圓心品質取決於房主選點，由出發點選點器（搜尋＋地圖微調）補償。

## Consequences

- 加入流程零定位權限請求；成員個資面不含任何座標。
- 未來若要復活中位數圓心或「對所有人都近」類功能，需重新設計成員位置收集（含同意取得與刪除語意）——本 ADR 是那時的討論起點。
